## Is it efficient already?

On the engine side, mostly yes. Fused add/sub accumulator updates, lazy accumulators, the Lizard SCReLU trick and no king buckets are close to state of the art for a 768→(1024×2)→1×8 net.

I benchmarked the original and patched loaders on the same net, measured in ns per call. "Eval" is an incremental evaluation in a search-like loop; "refresh" is a full accumulator rebuild plus eval:

| Build | Original eval / refresh | Patched eval / refresh |
|---|---|---|
| Runtime dispatch | ~320 / ~3300 | ~330 / ~1550 |
| `-mavx2` | ~295 / ~3190 | ~300 / ~1490 |
| `-march=native` (AVX-512) | – | ~250 / ~1190 |

What the numbers mean:
- **Evals on AVX2:** unchanged. There was little left to gain.
- **Refreshes:** about 2.1× faster, from the new register-tiled accumulator kernel. This kernel is also used for captures and castling.
- **AVX-512 CPUs:** evals about 17% faster.
- **Compiler flags:** building with `-O3 -march=native` (or at least `-mavx2`) is worth another 5–10% over runtime dispatch.

How much of this shows up as NPS depends on eval's share of search time. The search itself may offer bigger wins, such as skipping evals you don't need or reusing the TT static eval.

On the training side, I changed the model's output layer to one matmul followed by a bucket gather. It gives identical results and is about 15% faster per step on CPU. The likely real bottleneck is `nnue_dataset.py`, which you didn't upload. If it decodes samples one at a time in Python, loading the data into memory and decoding whole batches with vectorized code would probably help more than anything else.

For data prep, the bottleneck is Hugging Face streaming. The patch selects only the columns it needs. Downloading the parquet shards and reading them with pyarrow would be faster still.

## Bugs, in order of impact

**1. The training labels are noisy (`prepare_data.py`).** The Lichess dataset has one row per (position, evaluation, principal variation). That's about 482M rows for about 191M positions, and most rows score worse moves in MultiPV analysis, not the position itself. Your script trained on all of them.

A real example: one endgame position is mate-in-26 at depth 55, but a shallower row scoring it 0cp also passed your filters and was kept as a draw label. It also creates near-duplicate adjacent rows and leakage between train and val. Lichess's own guidance is to use the first principal variation of the deepest evaluation. The patched script does that: on a sample, 9 kept rows became 3 correct labels.

**2. There's no weight clipping, which can silently break engine evals.** The engine's fast AVX2 kernel multiplies 16-bit values. If any quantized output weight exceeds ±128 (float ±2.0), that multiply overflows. I reproduced this: with an unclipped test net, the original loader gave wrong evals on 50/50 test positions. The 16-bit feature accumulator can also overflow if weights grow large.

The patched `train.py` clips to ±1.98, as bullet does. The patched loader also checks the weights at load time and falls back to an exact (slower) kernel if they're too large. So your existing net will evaluate correctly either way.

**3. Conventions I couldn't verify, but which must match the engine.** These live in files you didn't upload:
- **Target POV:** the dataset's cp and mate scores are from White's point of view. Training targets must be negated when Black is to move, and the sigmoid scale must be 400.
- **Square numbering:** must be a1=0.
- **Piece order:** must be P,N,B,R,Q,K = 0..5. If your `PTYPE_OF` returns 1..6 (Stockfish-style, which the `byTypeBB[ALL_PIECES]` naming hints at), every feature index shifts and the king index runs past the table.

**4. `train.py` issues:**
- Shuffling was off by default, on data that arrives in stream order.
- Resuming mid-epoch restarted the whole epoch.
- The default `--save-interval` of 2000 is larger than the ~976 batches per epoch at 8M positions, so only Ctrl-C ever saved mid-epoch.
- `batch_idx` wasn't reset per epoch, so pressing Ctrl-C early in the next epoch could mark an untrained epoch as complete.
- Calling `loss.item()` every batch forced a GPU sync.

**5. Loader edge cases:**
- A failed reload left half-overwritten weights active.
- A bad explicit path silently fell back to the default net.
- `nnue_eval` dereferenced `pos->search` without a NULL check.
- Deep plies could reuse a stale accumulator slot.
- `aligned_alloc` doesn't exist on Windows/MinGW.
- File size was never validated.

## What the patched files do

- **`nnue_loader.h`:** same API and file format. Fixes everything in (5), adds the exact-kernel fallback from (2), adds the faster refresh and AVX-512 paths, and documents the build flags.
- **`check_net.py`** (new): verifies a net file. It checks file size and the overflow bounds, and computes bit-exact reference evals that should match your engine exactly. With `--checkpoint` it compares float and quantized outputs. With `--pipeline` it runs positions through your real dataset code and flags feature, bucket, or POV mismatches.
- **`train.py`:**
  - `--clip`, defaulting to 1.98.
  - Shuffling on by default, with a `--seed` option.
  - Exact mid-epoch resume at the saved batch, with correct Ctrl-C saves.
  - No per-batch GPU sync.
  - `--init`, to fine-tune an existing net on new data with a fresh optimizer.
- **`prepare_data.py`:** keeps one correct label per position.
- **`model.py`:** the faster output layer.
- **`export_weights.py`:** warns about overflow risk at export time.

Now the cleanup script for the existing cache.Yes, you can keep it and don't need to re-download anything. The file format is unchanged, so all the new files read it directly. But used as-is, it still has the label problem: each position appears several times, most copies carry the score of a worse move, and most val positions are also in train. `clean_cache.py` repairs this in one pass over your existing files and writes new ones, so the originals are never touched.

It does three things:
1. **Keeps one label per position.** Copies of a position sit next to each other in your file, so it merges each group into one record and keeps the score that's best for the side to move. That is the best move's score.
2. **Fixes val.** It removes duplicates from val and corrects each val label using that position's copies in train.
3. **Removes val positions from train**, so validation measures generalization again.

I tested it by running your original `prepare_data.py` on a simulated dataset with the same row structure as the Lichess one:
- Average label error dropped from 110cp to 3.8cp.
- 85% of labels became exactly the correct score.
- Positions shared between train and val went from 4,672 to 0.

On the real rows we looked at earlier, it recovered the correct 69cp and 35cp labels.

One case it can't fix: positions whose best line was a forced mate. Your original run dropped mate rows, so for those only a worse line's score survived. The mate-in-26 endgame is an example; it stays labeled 0. The records don't show which positions are affected, so I can't tell you how many there are.
